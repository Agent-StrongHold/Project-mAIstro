# SPEC-082926-25a2: AC-State Per-Branch Notes

- **Status:** Active
- **Decision:** ADR-082926-25a2
- **Closes:** #585

## Scope

`scripts/check-ac-state.py`'s `--ratchet`/`--bank` machinery, the ledger files it
reads and writes, and the fold that replaces them.

Out of scope: what the ratchet *means* — the same eleven counters in the same
directions — and the other ledger ratchets, which are #319's.

## The note

One file per branch under `quality/ac-state-notes/`, named from the branch:

```json
{
  "branch": "claude/issue-333-no-silent-ephemeral-downgrade",
  "measured_with_tests": true,
  "counters": { "design_coverage": 22.0915, "specs_awaiting_retrofit": 139, ... }
}
```

`_baseline.json` is the same shape with no branch, seeded from the retired
`quality/ac-state-ceilings.json` so no bound loosens across the change.

## The fold

| counter class | direction | fold |
|---|---|---|
| the ten debt counters | lower is better | **minimum** across notes |
| `design_coverage` | higher is better | **maximum** across notes |

Both folds are monotone, so the bound can only tighten as notes accumulate.

**Which notes.** Those present at the **base revision**, resolved through
`ratchet_provenance`. The candidate's own note is written by `--bank` and is
deliberately excluded from the fold it is judged against — a note that could
relax its own bound would be the self-approving oracle #534 closed.

A note therefore enters the bound only by merging, which is also why an
abandoned branch cannot leave behind a floor the trunk cannot meet (#508).

## Acceptance Criteria

```gherkin
Feature: AC-state per-branch notes

  @AC-1
  Scenario: Two branches from one base do not collide
    Given two branches cut from the same base
    And each raises design coverage and banks its own note
    When the two changes are combined
    Then no quality/ac-state path conflicts between them

  @AC-2
  Scenario: The fold keeps both contributions
    Given two merged notes recording different design coverage
    When the bound is folded
    Then it is the higher of the two
    And neither note has been overwritten

  @AC-2
  Scenario: The fold tightens every debt counter
    Given two merged notes recording different debt counts
    When the bound is folded
    Then each counter takes the lower of the two

  @AC-3
  Scenario: A regression is still refused
    Given a candidate measuring below the folded floor
    When the ratchet runs
    Then it fails and names the counter, the measurement and the bound

  @AC-3
  Scenario: A candidate cannot launder a regression through its own note
    Given a candidate whose own note claims a lower floor
    When the ratchet runs against the base-resolved fold
    Then the candidate's note does not enter the bound
    And the regression is still refused

  @AC-3
  Scenario: A candidate cannot loosen the bound by editing a merged note
    Given a candidate that rewrites another branch's note to a weaker value
    When the ratchet runs
    Then the bound is unchanged, because it was read at the base revision

  @AC-4
  Scenario: A note that contributes nothing is stale and compactable
    Given a note every counter of which is dominated by the fold of the others
    When compaction runs
    Then that note is removed
    And the folded bound is unchanged

  @AC-4
  Scenario: A note that still contributes is not removed
    Given a note holding the strongest value of some counter
    When compaction runs
    Then that value survives in the baseline
    And the folded bound is unchanged

  @AC-5
  Scenario: The per-decision measurement is not committed
    Given the measurement file is generated by a run
    When the repository is inspected
    Then quality/ac-state.json is ignored rather than tracked
    And the bound does not depend on it

  @AC-6
  Scenario: A failure says what to do
    Given a ratchet failure under the note scheme
    When the message is printed
    Then it names the folded bound, where it came from, and the exact bank command
```
