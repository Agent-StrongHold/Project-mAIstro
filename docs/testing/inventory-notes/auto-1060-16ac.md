# auto-1060-16ac — replay-truthful receipt protocol, continued

Seven maistro-core node IDs and two root-suite node IDs continue the #1060
durable-receipt work already recorded in `1060-durable-event-replay.md`.

## packages/maistro-core/tests: +7

- **+3** — `test_append_rejects_non_strict_json_payloads`
  (`test_durable_store_conformance.py`, parametrized over the memory, SQLite
  and PostgreSQL stores). `request_digest_v1` serializes the logged body with
  `allow_nan=False` before the receipt claim, so a NaN/Infinity payload that
  survived append would raise on every tick and wedge the cursor on that
  event forever — no receipt could ever be claimed or settled. The append
  path of all three backends now rejects non-strict-JSON payloads, and the
  test pins rejection-then-success across all three stores.
- **+3** — `test_success_settles_never_bypass_begin_dispatch`
  (`test_durable_store_conformance.py`, same three backends).
  `validate_settle` gated SUCCESS on acknowledgment alone, so a
  token/revision-current caller could terminal-settle a claimed receipt with
  zero attempts and no dispatch marker — unreclaimable despite nothing
  having been sent. Acknowledged evidence now additionally requires
  `dispatch_started_at`, enforced once in the shared validator so the three
  backends cannot drift.
- **+1** — `test_malformed_handler_url_is_a_pre_send_refusal`
  (`test_processing.py`). `httpx.InvalidURL` sits outside the `HTTPError`
  hierarchy, so a syntactically malformed `handler_url` left to the caller
  would surface as an indeterminate possibly-committed call and settle
  UNKNOWN after consuming every attempt for a call that could never start.
  `_unsendable_target_reason` now refuses a missing or malformed target
  before `begin_dispatch`, and the test pins the pre-send FAILED settlement
  (`handler_url_malformed`, the httpx detail in `last_error`, no physical
  call, cursor advanced).

## tests/: +2

`tests/migrations/test_durable_delivery_receipts_downgrade.py` walks the real
alembic chain against PostgreSQL for the 064 downgrade. Revision-063's
`InvocationStatus` has no `UNKNOWN` member, so a leftover `'unknown'` receipt
after a downgrade would crash the rolled-back runtime's row decoder on first
touch. The downgrade reclassifies `unknown` receipts to 063-era terminal
`failed` (tagging `last_error` for operators) and the tests pin both the
decode-safety invariant — statuses must stay inside the spelled-out 063-era
set, because the live enum gained `unknown` and would decode the regression
vacuously — and the re-upgrade round trip (fail-closed re-derivation via
`legacy_failed_unproven`, no key reinvented, historical SUCCESS and
unattempted pending rows untouched). Both tests were shown to fail against
the un-fixed downgrade.
