# auto-1150-a2a5: the authority re-check on the writing connection (#1150, P1)

## What moved

The Workspace store boundary decided the acting principal's authority
*before* the write took the Workspace's serialization point. An owner demoted
or removed in between could still add, promote or demote members: the check
had answered about a roster that had already changed (the P1 review finding on
this branch's PR).

The decision now happens twice, with one rule:

* the pre-write check stays the fast refusal (an outsider takes no lock, an
  unknown Workspace does not become an existence oracle);
* the authoritative check is re-decided on the connection that will do the
  write, after the Workspace's own serialization point -- the PostgreSQL row
  lock, SQLite's `BEGIN IMMEDIATE` -- so the read that decides is serialized
  with the revocation it races.

Both answers come from the same decision function (`decide_workspace_action`,
shared with `WorkspaceAuthorizer`), so the re-check cannot drift from the
rule it re-checks and there is still exactly one authorization path.

## The tests (+6 node IDs: 3 cases over 2 durable backends)

`packages/maistro-core/tests/workspaces/test_store_boundary_authority_race.py`
revokes the owner's membership *between* the store's two reads -- the
pre-write check answers from the stale membership, exactly as it would if a
demotion had committed in that window -- and then asserts the mutation is
refused and no membership row was written, for both the add and the removal
path. The third case is the control: with the authority intact the same
mutation still succeeds, so a refusal cannot be vacuous.

The in-memory reference is deliberately not in this suite: it has no await
between its decision and its write, so it cannot be the store that races.
