# M1 #1161 — the container closes both SQLite connections it opens

Five new test functions appended to
`packages/maistro-core/tests/test_container_pool_ownership.py`, after the
existing #335 pool-ownership tests. No existing test is removed or weakened.

The production change gives `Container.aclose()` ownership of the SQLite
connections the same way it already held the asyncpg pool: when the container
opened them (`holds_db_pool`, set by `create_container`'s sqlite branch), it
closes the shared `db_pool` and the session store's own `session_conn` (#327)
exactly once, each behind its own try/except so one failing close cannot strand
the other, and a caller-supplied connection is left for its owner. The
docstring records the shutdown semantics — aiosqlite's `close()` drains queued
operations before releasing, and its worker thread is a non-daemon thread, so
an unclosed connection blocks interpreter exit.

The new tests pin the rule rather than trusting the prose:

- a real container built on file-backed SQLite closes both connections on
  `aclose()`, nulls both fields, clears the flag, and a use of either
  connection afterwards fails loudly;
- a connection the caller supplied survives `aclose()` untouched and usable;
- a second `aclose()` closes each connection exactly once (a
  `FakeSqliteConnection` counts its own closes — same discipline as the #335
  tests: count, don't trust);
- when one connection's `close()` raises, the other is still closed, the
  container still ends closed with both fields nulled, and the failure is
  logged;
- after `aclose()` plus garbage collection, no aiosqlite `ResourceWarning`
  ("deleted before being closed") is emitted.

Like the pool tests above them, the SQLite tests run anywhere — they build real
containers on `sqlite:///<tmp>/...` and need no database server, and none of
them stakes an `ac` criterion.
