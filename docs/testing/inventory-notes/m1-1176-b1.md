## Repair round 2 (this worktree)

Audit finding `idempotency.py:1236-1248` — *returns `InMemoryTaskIdempotencyStore`
after configured PostgreSQL provisioning failure, violating the
no-process-local-cache stop condition* — was the one live item: the earlier
repair commit (`a2feb6c1`) had already closed the claim-fence and
ambiguous-window findings (`queue.py` begin-before-mint + token fences +
compensation; the death-after-mint / death-before-mint tests), the durable
server E2E had replaced the in-memory-runstore restart simulation with real
SQLite claim files and fresh connections, and the PR-head mismatch is a
GitHub-plumbing observation this worktree cannot act on (no GitHub mutations).

Repairing the finding exposed that the real defect was **tier selection**, in
both directions. `wire_task_idempotency` landed claims on any configured
`pg_pool`, while `wire_execution_spine` lands Runs there only when
`spine_is_migrated` passes — so the container's own comment ("Same backend the
spine just chose") was false whenever a pool was configured but unmigrated:
durable claims beside an in-memory spine make a restart-retry *replay a
receipt whose Run died* — a false reconciliation, work silently lost. The
opposite corner was the audited one: provisioning failure degraded claims to
process-local beside a spine that might be durable, minting a second Run for
the first retried submission after a restart. The repair makes the container's
promise true by construction:

- `runs/wiring.py`: the probe goes public as `spine_is_migrated` (one
  definition — the tiers cannot drift on which pool is durable).
- `tasks/idempotency.py`: claims land on the pool only when the spine's probe
  says the spine lives there; provisioning failure on a spine-ready pool now
  raises `ConfigError` and the process does not start (fail-closed — no
  process-local fallback on a configured healthy PostgreSQL); a pool the spine
  refused gets no claims at all, which follow the spine down to SQLite or
  in-memory, loudly. The deferred import is forced: `runs.wiring` imports
  `tasks.admission`, which imports this module.

**Reconciliation note (issue text vs convention).** The spine's accepted
convention (`spine_is_migrated`, with #122/#132 provenance in its docstring)
is loud-degrade, never startup-crash, for a configured pool the spine itself
cannot make durable — and claims-in-memory beside an ephemeral spine is the
honest tier there, not a cache in front of durability. The one case this
repair still refuses to start for is a spine-ready pool whose claims DDL is
refused: durability asymmetry against a *healthy* database is a
misconfiguration, and the wire says so.

## Repair round 3 (this worktree) — executed-probe evidence closed

The verify pass on `d1f31c78` ran live probes against the runtime, and two of
its three code findings were real defects in production behavior (the third
was a GitHub-plumbing observation this worktree cannot act on). Both are
repaired here, each reproduced first and re-run to green:

**Migration 034 vs runtime self-provisioning.** Reproduced on a temporary
PostgreSQL: database at revision 032, `PgTaskIdempotencyStore.ensure_schema()`
provisions the claims table at wire time (the documented behavior — wiring
does not wait for the chain), then `alembic upgrade head` exited 1 with
`DuplicateTable: relation "task_idempotency" already exists`. A chain that
cannot reach head on exactly the deployments that provisioned early is broken
at the command every documented setup path runs. The upgrade now inspects what
is standing: all ten columns present → adopt the runtime's table (create the
purge index if the provisioning half-failed, stamp the revision); columns
missing → a loud refusal naming the missing columns, never a stamp over a
foreign shape. Columns are spelled once (`CLAIM_COLUMNS`) so the create and
the check cannot drift. Tests: `tests/migrations/test_migration_chain.py`
gains `TestTheChainSurvivesRuntimeSelfProvisioning` (+2, real-server gated
like the rest of that file) — the provision-then-upgrade sequence driven
through the real `ensure_schema`, and the refusal edge, which also cleans up
its foreign table because the `empty_database` fixture can only downgrade what
the chain owns. Executed: full migration file 13 passed against a live
PostgreSQL, and the round-trip/refusal paths verified by hand.

**The crash-after-create window stranded the Run it reconciled to.**
Reproduced at the queue seam: a claimant dying after minting its Run but
before the receipt reached any queue left the claim resolving — by the
contract's own terms — to a Run stuck at `created`, a replayed receipt saying
`queued`, and a restarted queue holding nothing: reconciliation answered the
retry while silently stranding the work. The replay path now finishes the
crash victim's own last step: `record_transition(run_id, QUEUED)` is the gate
(true exactly when the Run is CREATED or QUEUED — it advances a CREATED Run
and refuses RUNNING/terminal work that re-enqueuing would duplicate), and the
reconstructed receipt re-materializes into the queue the reconciling retry
landed on. Two racing replicas re-enqueueing the same QUEUED Run is still
safe: the Run spine refuses the second QUEUED→RUNNING, so the loser's task
fails visibly rather than executing twice. No spine → no Run state to consult
→ receipt replays unqueued (the no-database tier's documented ephemerality).
Tests: core `test_idempotency.py` gains the crash-between-mint-and-queue
resumption test and the RUNNING refusal-edge test (+2), and the
restart-replay test now asserts the reconciled work is executable rather than
asserting the old stranding (`receipts == []`). Server E2E gains the test the
contract actually describes (+1): a genuine client-side timeout
(`asyncio.wait_for` around the POST) that cancels the request mid-admission
*hanging at the outcome record* — the ambiguous crash-after-create window —
over the fully durable tier (SQLite claim file AND SQLite Run spine, each
"process" opening its own connections), then a restart, a lapsed lease, and a
retry asserted to reconcile to the same task/run ids by discovery AND to leave
the restarted queue handing the work to a runner. The prior E2E that this
replaces the *claims* of (it answered the first POST and reused one in-memory
RunStore) is kept, honestly reworded, for what it still proves: receipt and
header-key echo across a restart of a completed admission. Executed: core
tasks suite 320 passed / 1 skipped, server api suite 349 passed, the focused
idempotency files green, and the durable file 27 passed *against a real
PostgreSQL* (`MAISTRO_TEST_PG_DSN`), including the wiring-decision test the
previous round left skipped.
