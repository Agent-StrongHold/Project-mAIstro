# M2-A #1173 — externally rooted `users.toml` tamper evidence

`packages/maistro-core/tests/privilege/test_privilege.py` keeps the existing
valid-load test and replaces the old unsigned byte-mutation check with the
audit's attacker model: arbitrary `users.toml` contents name an
attacker-controlled admin key, alter users and roles, add permissions, and
carry a matching HMAC generated with that attacker key. The external host key
rejects the forgery.

The forgery tests encode the exact audit constructions and are discriminating
against the pre-fix (6c4aa4bb) verifier, which authenticated with the LAST
admin entry's `public_key` (last-admin-wins):

- `test_refuses_exact_forged_self_key_construction` writes the single-admin
  attacker file (admin `eve`, attacker key, `permissions = "*"`) and signs it
  with the attacker key — the construction that LOADED on pre-fix code as
  `admin=eve/attacker-controlled-key`.
- `test_refuses_forged_last_admin_anchor_construction` keeps a plausible first
  admin and appends the attacker as the LAST admin, signing the whole file with
  the attacker key — the construction the pre-fix last-admin-wins anchor
  accepted wholesale.

Both tests first assert the forgery carries a signature VALID under the legacy
file-parsed anchor (via a local replica of the 6c4aa4bb selection plus the
module's `_verify`), proving rejection comes from the external trust root and
not from a malformed signature; reverting the verification anchor to a
file-parsed key makes these tests fail because the store then loads the forged
file.

Three further node IDs are added:

- `test_authenticated_trust_root_migration_via_public_api` proves the
  documented SPEC-012 rotation/recovery migration using only the shipped
  public API: constructing the store bound to the current external secret
  authenticates the artifact (an attacker-nominated current key raises
  `UsersTamperError` and aborts before any write), re-initializing a store
  bound to the new external secret re-signs the verified roster, and only the
  new root is authoritative afterwards. `UsersStore` deliberately has no
  file-triggerable rotation method — a prior method-based API was removed
  rather than shipped as production-unused surface.
- `test_file_cannot_initiate_or_authorize_rotation` proves the file cannot
  choose or trigger its own authority: a users.toml carrying an
  attacker-nominated `trusted_signing_key` directive plus a matching attacker
  HMAC is rejected under the legitimate root, and the store's public surface
  is exactly `{initialize, admin, user_by_public_key}` — no migration entry
  point consumes anything from the file.
- `test_empty_external_trust_root_is_rejected` proves the verifier cannot run
  without independently supplied trust material.
