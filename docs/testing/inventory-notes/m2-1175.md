  clears `last_outcome`; a drained scope reports backlog gauge 0; a
  batch-limited sweep reports backlog gauge 1 under its mode label; a failed
  sweep withdraws the standing backlog report.

The purge API itself changed shape: `purge_expired_runs(scope, *, now,
limit)` takes a required `RetentionScope` (a `WorkspaceRetentionScope`, or a
`GlobalRetentionScope` carrying an `authorized_by` grant), and returns a
`PurgeOutcome` — scope, per-class dependent counts (runs / node_runs /
attempts / continuations / event references retained / schedule claims
released), and `backlog_remaining` — which `RunRetentionSweeper.last_outcome`
exposes and `maistro_retention_purged_total{mode}` aggregates. The SQLite and
PostgreSQL purges push the Workspace predicate into the candidate SELECT and
handle dependent evidence in the purge transaction: `graph_continuations`
(migration 021, no FK) is deleted with its Run; `canonical_event_log`
(migration 030) is kept and counted. Health surfaces the scope-and-backlog
terms, not a raw count: `maistro_retention_purged_total{mode}` for volume,
and `maistro_retention_backlog_remaining{mode}` — set from the outcome's
`backlog_remaining` after each completed sweep, withdrawn on failure — for
"the batch ran out before the scope drained", the state a retention alert is
about. The dependent-reference inventory in `retention_scope` additionally
names the producer-provenance tables (learnings / outcomes / design_outputs /
episodic_memories, migrations 026/028/031) in the preserve class alongside
tasks and session turns.
